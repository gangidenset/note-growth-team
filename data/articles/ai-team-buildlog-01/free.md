# Claude Code で「AI社員チーム」を作るときに最初に決めた5つの安全ルールと、実際に起きた6つの失敗

- 確認日: 2026-10-23
- 動作確認した環境: 筆者のクラウド実行環境（Claude Code 2.1.309）と、筆者の Windows / PowerShell（出典: 制作ログ docs/progress.md の「環境確認結果」）
- Claude Code の機能や設定の書き方は、バージョンによって変わる可能性があります。ここに書いたのは「この環境でこう動いた」という記録です。

## この記事は誰のどんな悩み向けか

Claude Code や AI エージェントを使い始めると、こんな不安が出てきませんか。

- AI に作業を任せたら、勝手に公開・削除・課金をされないか
- AI が「それっぽい数字」をでっち上げて、記事や資料に書いてしまわないか
- API キーなどの秘密情報を、AI が読んだりログに出したりしないか

この記事は、筆者が note 用の「AI社員チーム」（市場調査・マーケティング・執筆・品質チェックの4担当）を Claude Code で作ったときに、**AI に勝手なことをさせないために決めたルールと仕組み**、そして**実際に起きた失敗**をまとめた制作ログです。

先に正直に書いておくと、このチームは「note で月5万円の売上」を目標にしていますが、**この記事の時点で売上はまだゼロです**。稼ぎ方の記事ではなく、AI に任せる範囲と人間が握る範囲をどう分けたか、の記録として読んでください。

## 筆者について

Claude Code の利用歴はまだ浅いです。これまでは自分でコードを書く機会が多かったのですが、Claude を使うとデモアプリやスマホ用アプリの開発が簡単にできることを実感しました。今後の AI の活躍に期待している一人です。

Claude の Pro プランにも課金しているので、何か収益化できることはないかと考え、note の記事作りに取り組むことにしました。

## 作ったもの: 4人のAI社員と「進行役」

Claude Code には、役割ごとに別の AI（Subagent）を定義できる仕組みがあり、このチームではそれを使っています。設定ファイルは `.claude/agents/` に置いた Markdown ファイルです（出典: docs/architecture.md §2.2）。

| 担当 | 主な仕事 | 使える道具（このチームでの設定） |
|---|---|---|
| 市場調査（market-researcher） | テーマ候補や競合記事を、出典付きで記録 | ファイルの読み書き、Web検索、Webページ取得 |
| マーケティング（marketing-strategist） | テーマ選定・価格・無料→有料の導線 | ファイルの読み書き |
| 編集・執筆（editor-writer） | 無料記事・有料記事の下書き | ファイルの読み書き |
| 品質・分析（quality-analyst） | 公開前チェック・捏造検知 | ファイルの読み取りと、チェック結果の書き込み |

（出典: .claude/agents/ の各ファイルの tools 欄）

この4人に仕事を割り振るのが、Claude Code のメインの会話（このチームでは「進行役」と呼んでいます）です。どの担当にも、**承認・公開・削除・課金・外部送信の権限は持たせていません**（出典: docs/architecture.md §2.2）。

全体の流れは次のとおりです。

1. 市場調査 → テーマ選定 → 無料記事・有料記事の下書き → 品質チェック（ここまでが AI）
2. 人間（筆者）が内容を確認して承認
3. 人間が note の画面で手動投稿し、公開URLを記録

設計書には、この考え方を一文で書いています。

> AIが書けるのは下書きと記録まで。承認と公開は人間の手元でしか起きない
>
> （出典: docs/architecture.md §1）

なお、note への投稿は自動化していません。個人クリエイター向けの公式APIがないことを確認したうえで、手動投稿にすると決めました（出典: docs/tech-decisions.md ADR-006）。

## 最初に決めた5つのルール

Claude Code は、プロジェクトのルールを `CLAUDE.md` というファイルに書いておくと、それを読んで作業します。このチームでは、次の5つを最優先のルールとして書きました（出典: CLAUDE.md）。

### 1. 捏造禁止

他人の記事の購入数や売上など、公開されていない情報を作らない・断定しない。分からなければ「不明」と書く。

他人の記事の販売数は原則として公開されておらず、外から見えるのは価格・スキ数・公開日などの表示されている値だけ、という前提で設計しています（出典: docs/requirements.md §6）。見えない値を推測で埋めないよう、「分からないものは分からないと書く」を明文化しました。

### 2. 出典必須

市場データには、出典URL・取得日時（タイムゾーン付き）・取得方法・「実際に見た値か、推定か」の区分を記録する。推定なら、その根拠も書く。

これは後で、AI が「取得日時を適当に埋める」という失敗を見つけるきっかけにもなりました（後述）。

### 3. 承認は人間だけ

記事を「承認済み」「公開済み」にできるのは人間だけ。承認用のコマンドは AI に実行させない。

### 4. 不可逆操作は事前確認

課金、外部送信（メール・SNS・フォーム・Webhook）、公開、削除、Git 履歴の書き換えは、オーナーが明示的に承認してから行う。

### 5. 秘密情報を扱わない

`.env`（APIキーなどを置くファイル）を AI に読ませない・表示させない・Git に入れない。

## ルールは「書くだけ」では足りなかった

ここが一番伝えたいことです。`CLAUDE.md` に「承認は人間だけ」と書いても、それは AI へのお願いにすぎません。設計書では、ルールだけでは AI が誤って承認済みにする余地が残る、という理由から、複数の仕組みを重ねることにしています（出典: docs/tech-decisions.md ADR-007）。

このチームで重ねた仕組みは次のとおりです（出典: docs/architecture.md §4、docs/progress.md）。

| 仕組み | 何をするか |
|---|---|
| CLAUDE.md | ルールを AI に伝える |
| 権限設定（.claude/settings.json） | 承認コマンドの実行や `.env` の読み取りを禁止、削除や外部通信は人間に確認 |
| フック（PreToolUse） | AI がコマンドを実行する直前に中身を検査し、承認コマンドなどを止める |
| 状態管理のプログラム | 「承認済み」「公開済み」への変更は、人間専用のコマンドでしかできない |
| 人間の端末チェック | 人間専用のコマンドは、Claude Code の中や自動実行からは動かない |
| 内容ハッシュ | 承認した版の本文を指紋（ハッシュ値）で記録し、1文字でも変わったら承認を無効にする |
| 整合性チェック | 承認記録と本文の食い違いなどを、まとめて検出する |

「1つが破られても、次で止まる」ようにするのが狙いです。実際、後で書くように、2つ目の権限設定は一度すり抜けられています。

## 実際に起きた6つの失敗（概要）

制作中に起きた問題は、すべて制作ログ（docs/progress.md）に記録しています。その中から6つを紹介します。

### 失敗1: 禁止したはずの承認コマンドが、書き方を変えると通ってしまった

権限設定で `npm run approve` を禁止していましたが、この禁止ルールは「先頭が一致するか」で判定されていたため、`npm run -s approve` のように途中にオプションを挟んだ書き方がすり抜けていました。
→ コマンドを実行直前に検査するフックを追加して解決しました。テストで20通りの書き方を確認しています（出典: docs/progress.md「解決済みの問題」）。

### 失敗2: 秘密ファイルの禁止範囲が広すぎて、見本ファイルまで読めなくなった

`.env.*` をまとめて禁止したところ、秘密情報を含まない見本ファイル `.env.example` まで AI が読めなくなっていました。
→ 禁止対象を具体的なファイル名に絞りました。そのかわり、リストにない名前の秘密ファイルは対象外になる、という注意点が残っています（出典: docs/progress.md「解決済みの問題」）。

### 失敗3: 調査担当が、取得日時に「00:00」を仮置きしていた

市場データの取得日時が、実際の作業時刻ではなく `00:00` になっていました。
→ 実際の作業時間帯の上限の時刻に直し、経緯をデータのメモ欄に残しました。再発防止として、「仮の時刻を書かない」「進行役が依頼文に現在時刻を書く」をルールに追加しました（出典: docs/progress.md「フェーズ3」）。

### 失敗4: 調査担当が、未来の時刻を取得日時に書いていた

別の調査では、作業にかかった時間を見積もって時刻を書いたため、実際より先の「未来の時刻」が記録されていました。
→ 実作業の上限の時刻に直し、経緯を記録しました（出典: docs/progress.md「テーマ候補調査」）。

### 失敗5: 進行役（メインの会話）自身も、未来の時刻を書いた

調査担当だけでなく、指示を出す側の進行役も、更新日時に未来の時刻（実際は 15:06 なのに 15:10）を書いていました。
→ 修正したうえで、「5分以上先の日時」を自動で検出するチェックを追加しました（出典: docs/progress.md「フェーズ3 の残り」）。

### 失敗6: 筆者が Windows で設定を1行飛ばし、「記事が見つかりません」になった

承認コマンドを練習用データで試したとき、練習用フォルダを指定する環境変数 `NGT_ROOT` の設定を飛ばしてしまい、エラーになりました。
→ 練習用データを作るコマンドの案内を OS 別・番号付きに改め、エラーメッセージに「探した場所」を表示するようにしました（出典: docs/progress.md「オーナーに確認してほしいこと」）。

PowerShell をまだ使いこなせておらず、練習用フォルダを指定する手順を省いて記事を探そうとしてしまいました。小さなミスですが、手順はちゃんと順番どおりに踏まないといけないと再認識しました。

## この制作で分かったこと

上の失敗から、このチームでは次のように考えるようになりました。

- **禁止ルールは「書き方の違い」ですり抜けることがある。** 1つの仕組みに頼らず、重ねておく。
- **AI は分からない値を「それらしく」埋めることがある。** 時刻のような地味な項目こそ、自動チェックで見張る。
- **指示する側（進行役）も間違える。** 担当 AI だけでなく、全体を同じチェックにかける。
- **人間の操作ミスも起きる。** 手順は番号付きで書き、エラーには原因の手がかりを出す。

調査は AI が自動でやってくれるので、とても便利です。ただ、作業環境の設定で特定のURL（note の公式サイトなど）へのアクセスを許可しないと、調査が十分にできないことに気づきました。許可したあとは、公式ページを直接開いて数値を照合できるようになりました。

作業のほとんどを AI にやってもらっているので、自分がどこで失敗したのか気づかないくらい、AI のカバー力がすごいと感じています。
