# Claude Code で「AI社員チーム」を作るときに最初に決めた6つの安全ルールと、実際に起きた6つの失敗

- 確認日: 2026-10-23
- 動作確認した環境: 筆者のクラウド実行環境（Claude Code 2.1.309）と、筆者の Windows / PowerShell[1]
- Claude Code の機能や設定の書き方は、バージョンによって変わる可能性がある。ここに書いたのは「この環境でこう動いた」という記録だ。

## この記事は誰のどんな悩み向けか

Claude Code や AI エージェントを使い始めると、こんな不安が出てこないだろうか。

- AI に作業を任せたら、勝手に公開・削除・課金をされないか
- AI が「それっぽい数字」をでっち上げて、記事や資料に書いてしまわないか
- API キーなどの秘密情報を、AI が読んだりログに出したりしないか

この記事は、筆者が note 用の「AI社員チーム」（市場調査・マーケティング・執筆・品質チェックの4担当）を Claude Code で作ったときに、**AI に勝手なことをさせないために決めたルールと仕組み**、そして**実際に起きた失敗**をまとめた制作ログだ。AI社員を雇ったら、まず就業規則を書くことになった、という話でもある。

先に正直に書いておくと、このチームは「note で月5万円の売上」を目標にしているけど、**この記事の時点で売上はまだゼロだ**。目標までの距離は、今のところ5万円まるごとだ。稼ぎ方の記事ではなく、AI に任せる範囲と人間が握る範囲をどう分けたか、の記録として読んでほしい。

## 筆者について

Claude Code を使い始めて、まだ日が浅い。これまでは自分でコードを書くことが多かったけど、Claude を使ってみたらデモアプリやスマホ用アプリがあっさり作れて驚いた。これからの AI にかなり期待している。

Claude の Pro プランにも課金しているので、何か収益化できることはないかと考えて、note の記事作りに取り組むことにした。

## 作ったもの: 4人のAI社員と「進行役」

Claude Code には、役割ごとに別の AI（Subagent）を定義できる仕組みがあって、このチームではそれを使っている。設定ファイルは `.claude/agents/` に置いた Markdown ファイルだ[2]。

| 担当 | 主な仕事 | 使える道具（このチームでの設定）[3] |
|---|---|---|
| 市場調査（market-researcher） | テーマ候補や競合記事を、出典付きで記録 | ファイルの読み書き、Web検索、Webページ取得 |
| マーケティング（marketing-strategist） | テーマ選定・価格・無料→有料の導線 | ファイルの読み書き |
| 編集・執筆（editor-writer） | 無料記事・有料記事の下書き | ファイルの読み書き |
| 品質・分析（quality-analyst） | 公開前チェック・捏造検知 | ファイルの読み取りと、チェック結果の書き込み |

この4人に仕事を割り振るのが、Claude Code のメインの会話（このチームでは「進行役」と呼んでいる）だ。どの担当にも、**承認・公開・削除・課金・外部送信の権限は持たせていない**[2]。社員は4人いるけど、ハンコを持っているのは筆者だけ、という会社だ。

全体の流れはこうなっている。

1. 市場調査 → テーマ選定 → 無料記事・有料記事の下書き → 品質チェック（ここまでが AI）
2. 人間（筆者）が内容を確認して承認
3. 人間が note の画面で手動投稿し、公開URLを記録

設計書には、この考え方を一文で書いてある[4]。

> AIが書けるのは下書きと記録まで。承認と公開は人間の手元でしか起きない

なお、note への投稿は自動化していない。個人クリエイター向けの公式APIがないことを確認したうえで、手動投稿にすると決めた[5]。

## 最初に決めた6つのルール

Claude Code は、プロジェクトのルールを `CLAUDE.md` というファイルに書いておくと、それを読んで作業する。このチームでは、次の6つを最優先のルールとして書いた[6]。

### 1. 捏造禁止

他人の記事の購入数や売上など、公開されていない情報を作らない・断定しない。分からなければ「不明」と書く。

他人の記事の販売数は原則として公開されておらず、外から見えるのは価格・スキ数・公開日などの表示されている値だけ、という前提で設計している[7]。見えない値を推測で埋めないよう、「分からないものは分からないと書く」を明文化した。

### 2. 出典必須

市場データには、出典URL・取得日時（タイムゾーン付き）・取得方法・「実際に見た値か、推定か」の区分を記録する。推定なら、その根拠も書く。

これは後で、AI が「取得日時を適当に埋める」という失敗を見つけるきっかけにもなった（後述）。

### 3. 承認は人間だけ

記事を「承認済み」「公開済み」にできるのは人間だけ。承認用のコマンドは AI に実行させない。

### 4. 不可逆操作は事前確認

課金、外部送信（メール・SNS・フォーム・Webhook）、公開、削除、Git 履歴の書き換えは、オーナーが明示的に承認してから行う。

### 5. 秘密情報を扱わない

`.env`（APIキーなどを置くファイル）を AI に読ませない・表示させない・Git に入れない。

### 6. 既存ファイルを勝手に削除・全面上書きしない

変更は、差分が分かる形で行う。

……と、ここまで並べると立派な就業規則に見える。問題は、これが本当に守られるかどうかだ。

## ルールは「書くだけ」では足りなかった

ここが一番伝えたいところだ。`CLAUDE.md` に「承認は人間だけ」と書いても、それは AI へのお願いにすぎない。言ってみれば、壁に貼った張り紙だ。設計書では、ルールだけでは AI が誤って承認済みにする余地が残る、という理由から、複数の仕組みを重ねることにしている[8]。

このチームで重ねた仕組みは次のとおり[9]。

| 仕組み | 何をするか |
|---|---|
| CLAUDE.md | ルールを AI に伝える |
| 権限設定（.claude/settings.json） | 承認コマンドの実行や `.env` の読み取りを禁止、削除や外部通信は人間に確認 |
| フック（PreToolUse） | AI がコマンドを実行する直前に中身を検査し、承認コマンドなどを止める |
| 状態管理のプログラム | 「承認済み」「公開済み」への変更は、人間専用のコマンドでしかできない |
| 人間の端末チェック | 人間専用のコマンドは、Claude Code の中や自動実行からは動かない |
| 内容ハッシュ | 承認した版の本文を指紋（ハッシュ値）で記録し、1文字でも変わったら承認を無効にする |
| 整合性チェック | 承認記録と本文の食い違いなどを、まとめて検出する |

「1つが破られても、次で止まる」ようにするのが狙いだ。実際、後で書くように、2つ目の権限設定は一度すり抜けられている。しかも、すり抜けたのは「禁止」と書いた、まさにその承認コマンドだ[11]。

## 実際に起きた6つの失敗（概要）

制作中に起きた問題は、すべて制作ログに記録している[10]。その中から6つを紹介する。設定の穴もあれば AI社員のやらかしもあり、最後は筆者本人も出てくる。

### 失敗1: 禁止したはずの承認コマンドが、オプション1つで素通り

権限設定で `npm run approve` を禁止していたけど、この禁止ルールは「先頭が一致するか」で判定されていたため、`npm run -s approve` のように途中にオプションを挟んだ書き方がすり抜けていた。
`-s` を1つ挟んだだけで別人扱い。変装としてはかなり雑なのに、門番は見抜けなかった。
→ コマンドを実行直前に検査するフックを追加して解決した。テストで20通りの書き方を確認している[11]。

### 失敗2: 秘密ファイルを守りすぎて、見本ファイルまで締め出した

`.env.*` をまとめて禁止したら、秘密情報を含まない見本ファイル `.env.example` まで AI が読めなくなっていた。
失敗1とは逆で、今度は門番が厳しすぎて味方まで門前払いにしていた。
→ 禁止対象を具体的なファイル名に絞った。そのかわり、リストにない名前の秘密ファイルは対象外になる、という注意点が残っている[11]。

### 失敗3: 調査担当の取得日時が、9件そろって深夜0時

調査担当に手数料などの調査を頼んだら、返ってきた9件の記録の取得時刻が全部 `00:00` だった[12]。深夜0時ぴったりに9件まとめて調べる社員、夜型にもほどがある。
原因は、調査担当に時計代わりになる道具（コマンド実行）を持たせていなかったことだと考えられる。持たせなかったのは自分だ。
→ 実際の作業時間帯の上限の時刻に直して、経緯をデータのメモ欄に残した。再発防止として、「仮の時刻を書かない」「進行役が依頼文に現在時刻を書く」をルールに追加した[12]。

### 失敗4: 調査担当、深夜0時の次は未来から記録を送ってきた

別の調査では、作業にかかった時間を見積もって時刻を書いたため、実際より先の「未来の時刻」が記録されていた。
夜型を直したと思ったら、今度は未来人になっていた。
→ 実作業の上限の時刻に直し、経緯を記録した[13]。

### 失敗5: 注意する側の進行役（メインの会話）まで、未来の時刻を書いた

調査担当だけでなく、指示を出す側の進行役も、更新日時に未来の時刻（実際は 15:06 なのに 15:10）を書いていた。
ミイラ取りがミイラになった、というやつだ。
→ 修正したうえで、「5分以上先の日時」を自動で検出するチェックを追加した[14]。

### 失敗6: 最後は筆者。Windows で設定を1行飛ばし、「記事が見つかりません」

ここまで設定と AI のミスを並べてきたけど、最後のひとつは筆者本人だ。
承認コマンドを練習用データで試したとき、練習用フォルダを指定する環境変数 `NGT_ROOT` の設定を飛ばしてしまい、エラーになった。
→ 練習用データを作るコマンドの案内を OS 別・番号付きに改め、エラーメッセージに「探した場所」を表示するようにした[15]。

PowerShell をまだ使いこなせていなくて、練習用フォルダを指定する手順を省いて記事を探そうとしてしまった。小さなミスだけど、手順はちゃんと順番どおりに踏まないといけないと再認識した。

## この制作で分かったこと

上の失敗から、このチームでは次のように考えるようになった。

- **禁止ルールは「書き方の違い」ですり抜けることがある。** 1つの仕組みに頼らず、重ねておく。
- **AI は分からない値を「それらしく」埋めることがある。** 時刻のような地味な項目こそ、自動チェックで見張る。
- **指示する側（進行役）も間違える。** 担当 AI だけでなく、全体を同じチェックにかける。
- **人間の操作ミスも起きる。** 手順は番号付きで書き、エラーには原因の手がかりを出す。

つまり、間違えるのは AI社員だけではない。進行役も、筆者も間違える。

調査は AI が自動でやってくれるので、とても便利だ。ただ、作業環境の設定で特定のURL（note の公式サイトなど）へのアクセスを許可しないと、調査が十分にできないことに気づいた。許可したあとは、メインの会話（進行役）が note の記事ページを直接開いて、価格などの数値を照合できるようになった。

作業のほとんどを AI にやってもらっているので、自分がどこで失敗したのか気づかないくらい、AI のカバー力がすごいと感じている。
