# 技術選定の理由と代替案（ADR形式）

- 作成日: 2026-10-23
- 各項目は「決定 / 理由 / 代替案 / 見直し条件」で記録する。

## ADR-001 AI実行基盤: Claude Code の Subagents + Skills
- **決定**: 専門担当を `.claude/agents/` の Subagent、共通手順を `.claude/skills/` の Skill として定義する。
- **理由**: 追加のサーバーやフレームワークが不要で、初心者でもMarkdownで役割を編集できる。Subagent は独立したコンテキストで動くため、調査の大量情報がメイン会話を圧迫しにくい。ツール権限を担当ごとに絞れる。
- **代替案**:
  - Claude Agent SDK で独自エージェントを実装 → 自由度は高いがコード量・保守負担が大きい。定期自動実行が必要になった段階で再検討。
  - 他社のマルチエージェントフレームワーク → 学習コストが増え、Claude Code の権限設定と二重管理になる。
- **見直し条件**: スケジュール実行や無人運転が必要になったとき。

## ADR-002 実装言語: Node.js 22 + TypeScript
- **決定**: 状態管理CLIは TypeScript で実装し、Node.js 22（環境に導入済み）で動かす。
- **理由**: 環境に既に入っている。型でデータ構造（市場データ・状態）を表現でき、誤りをコンパイル時に検出できる。Claude Code 自体も Node 製で親和性が高い。
- **代替案**: Python 3.13（同じく導入済み）。データ分析には強いが、今回は小規模なCLIと検証が中心のため TypeScript を選択。分析が重くなったら分析部分のみ Python 追加を検討。

## ADR-003 データ保存: Git管理の JSON / Markdown ファイル
- **決定**: 市場データ・記事・状態・承認を `data/` 配下のファイルで管理し、監査ログは JSON Lines（追記専用）。
- **理由**: 差分がGitで見える（誰がいつ何を変えたか）。中断しても状態がファイルに残る。DB不要で初心者が中身を直接確認できる。
- **代替案**:
  - SQLite → 件数が増えたときの検索・集計に強い。数百件を超えて集計が遅くなったら移行。
  - クラウドDB（Supabase等） → 外部送信・課金が絡むため現段階では不要。
- **見直し条件**: 記事数が数百件を超える、または複数人で同時編集する場合。

## ADR-004 スキーマ検証: zod
- **決定**: 市場データ・meta.json・承認記録を zod スキーマで検証する。
- **理由**: TypeScript の型とバリデーションを一元定義でき、「出典が欠けたデータは保存不可」を確実に実装できる。
- **代替案**: JSON Schema + ajv（言語非依存で汎用的だが記述が冗長）。他言語からも検証したくなったら JSON Schema を生成して併用。

## ADR-005 テスト: Vitest
- **決定**: 単体テスト・状態機械テストに Vitest を使う。
- **理由**: TypeScript をそのまま実行でき設定が少ない。高速。
- **代替案**: Node.js 組み込みテストランナー（依存ゼロだがTS対応に追加設定が必要）、Jest（設定が多い）。

## ADR-006 note への公開: 手動投稿（自動化しない）
- **決定**: システムは「公開用パッケージ」を作るまで。投稿はオーナーが note の画面で手動で行い、URLを `publish:record` で記録する。
- **理由**: note には一般公開の公式投稿APIがない（当方認識。フェーズ2で再確認）。非公式APIやブラウザ自動操作は規約違反・アカウント停止・仕様変更による破損のリスクがある。公開は不可逆操作であり、人の手を必ず通す要件にも合致する。
- **代替案**: Playwright によるブラウザ自動投稿（環境には Chromium あり）→ 規約確認とオーナーの明示承認がない限り採用しない。

## ADR-007 承認ゲート: 状態機械 + 内容ハッシュ + 多層防御
- **決定**: 承認を記事本文の SHA-256 ハッシュに紐づけ、CLI・TTY確認・Claude Code 権限設定・フック・整合性テストの多層で強制する。
- **理由**: 「ルールに書いてある」だけではAIが誤って承認済みにする余地が残る。ハッシュにより「承認した版と公開した版が同一」であることを機械的に保証できる。
- **代替案**: GitHub の Pull Request レビューを承認とみなす → Gitに不慣れな段階では負担が大きい。将来の選択肢として残す。

## ADR-008 秘密情報: `.env` + `.gitignore` + Claude Code deny 設定
- **決定**: APIキーは環境変数（ローカルでは `.env`、クラウド実行では環境設定のシークレット）で渡す。`.env` はGit対象外、Claude Code からの読み取りを deny。
- **理由**: 最小限の仕組みで「Gitに入らない・AIの会話ログに出ない」を実現できる。
- **代替案**: 1Password CLI / OSのキーチェーン → より安全だが初心者には設定が重い。運用が安定したら検討。gitleaks の pre-commit 導入もフェーズ3で検討。

## ADR-009 Web調査: Claude Code の WebSearch / WebFetch（手動確認併用）
- **決定**: 公開ページの観測は WebSearch / WebFetch とオーナーの手動確認で行う。大量スクレイピングは行わない。
- **理由**: 利用規約・robots.txt・サーバー負荷への配慮。取得方法 `method` を記録し再現性を確保。
- **代替案**: 専用スクレイパー → 規約確認とオーナー承認後に限定的に検討。
